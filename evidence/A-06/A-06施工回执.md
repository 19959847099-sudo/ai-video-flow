## ComfyUI 官方接口判断

采用官方 Server API 与 API-format 节点图，使用图片上传、POST /prompt、GET /queue、GET /history/{prompt_id} 与 GET /view。Workflow 与 UI 导出 JSON 明确区分，状态按实际 prompt_id 匹配，失败不伪装完成。官方来源与细节见 [ComfyUI 接入说明](comfyui-integration.md)。

这是官方契约与本地 Fixture 验证，不是远程实例联通或模型执行验收。工作流中模型槽明确未配置，不能把结构合法等同于远程服务器已接受执行。

## 集成方式

app/comfy_adapter.py 包含 WorkflowBuilder、ComfyAdapter、FixtureTransport 三个薄职责。模型名、节点 ID、输出节点与参考图拼板在外围执行表示中；核心生产数据不绑定云厂商。

请求表示包含 multipart 图片上传、JSON 提交和图片 GET 查询参数；响应映射包括 prompt_id、pending / processing、History 成功或 execution_error、输出描述和二进制读取。Fixture 无 HTTP 客户端、Key 读取或网络回退。

## Image Generation Task

app/image_production.py 新增独立 ImageTask，purpose 区分 CHARACTER_REFERENCE、SCENE_REFERENCE、SHOT_FIRST_FRAME；purpose 同时表达预期输出用途。保存相关 Character / Look、Scene / State、Shot 快照、有效参考图、最终描述、尺寸、种子与 retry_of。

不强行复用 Video Task、不建设万能 Asset。任务与 Workflow 落盘后保存哈希，继续执行和追溯时检查；源资产描述修改不会重写旧任务。

## Workflow Builder

三个用途共享一个内置节点模板。生产文字进入 CLIPTextEncode，有效角色与场景 Reference 经现有 Pillow 合成输入拼板，绑定表保存各图来源、哈希和区域；图像真正连接至 VAEEncode / KSampler。最终经 VAEDecode / SaveImage 输出。

没有参考图时可使用 EmptyLatentImage；当前示例均有参考图。模型使用可配置远程槽，不下载权重、不安装节点。此拼板 img2img 模板只证明信息与执行图连接，尚不是经过视觉质量验证的角色一致性方案。具体示例见 [Workflow Mapping](workflow-mapping.md)。

## Character Reference

GUI 从现有角色及雨夜 Look 创建任务，生成可读 Fixture PNG，人工“采纳为当前 Look / State”。新增 Reference 进入同一角色，并绑定雨夜 Look；保留 source_image_result_id，可恢复源 ImageTask / Workflow。稳定身份 Reference 采纳路径亦实现并受明确按钮控制。

## Scene Reference

GUI 从现有便利店场景及雨夜 State 创建任务，生成图片后人工采纳至该 State。复用 Store.import_reference 的图片格式校验、哈希去重和相对路径存储。重启后角色与场景均可看到新增图片。

## Shot First Frame

现有白天 Shot 生成第一张候选，人工 Reject、修改描述、Retry 产生第二个任务和结果，再明确设为首帧。first_frames/<shot_id>.json 记录 result_id / task_id / shot_id / path / sha256，不依赖 latest 文件。

Shot 页面显示当前首帧 ID。已选首帧对应的角色/Look/场景/State 引用变化时，视频任务会阻止误用旧首帧；图像入口仍允许生成新候选。首帧与视频最终 Selected Take 分开。

## Result Ingestion

image_tasks/<id>/ 保存 task.json、workflow.json、输入拼板与 exchange.json；image_executions/ 保存状态、prompt_id 和快照哈希；image_results/<id>/ 保存实际 image.png 与 result.json。读取图片、核对尺寸、哈希及任务/执行关系后才判 completed。

当前验收副本有 6 份图像任务与 6 张实际 PNG：角色 1、场景 1、GUI 首帧 2、DSH 首帧候选 2。最后两张均未自动采纳。旧执行证据不为匹配后续请求表示整理而重写。

## Human Gate / Promotion

GUI 明确提供稳定参考图采纳、当前 Look / State 采纳、用作 Shot 首帧、Reject 和 Retry。生成成功本身不会修改资产关联。Reject 后才能 Retry；已采纳 Reference 不能直接 Reject。首帧可在多个合格候选之间显式改选。

角色/场景采纳写回资产关系，图像审核记录保留采纳用途与 Reference ID；首帧写独立 Shot 关联。所有操作使用原稳定 ID，禁止跨用途/资产错误采纳。

## Video Handoff

同一已接入 fal-ai/kling-video/o3/standard/reference-to-video 官方契约支持 start_image_url。本轮新增 Video Task 可选 first_frame 快照，Adapter 将其实际 PNG 字节映射为该字段；原 4 张 Character / Scene Reference 仍在 image_urls，没有静默丢弃。

GUI 真实生成新 fal Fixture Take 3，并通过 FFplay 播放实际 MP4。原 Take 2 保持 Selected，首帧选定没有替用户选择视频结果。视频 Review 显示当次首帧快照。

## DSH

复用官方 DeepSeek Harness 0.1.5-rc.2、原 Node 运行时与生产插件，新增 prepare_shot_first_frame。真实执行 get_shot_context → prepare_shot_first_frame → get_shot_context，通过官方工具服务触发并记录 tools/result 事件。

工具创建任务、工作流、Fixture 生命周期与实际 PNG，返回 human_review_required=true。没有 Promote / Select 工具。DSH 完成退出后，GUI 仍可预览未采纳候选，原首帧和 Selected Take 保持。

最终 trace：[dsh-final/trace.json](dsh-final/trace.json)；网络审计：[dsh-final/network-audit.json](dsh-final/network-audit.json)。没有 LLM 模型调用，也不声称自主 Agent 规划。

## GUI

保留 A-05 Tkinter / ttk 布局，只添加三个生成入口、一个薄图像/首帧审核页、Shot 首帧标签及视频首帧上下文。使用正常 GUI，无需手改 JSON、填写内部路径或搬运 Reference。

实际验证了正常尺寸、最小窗口、完整关闭重启、Reference 回读、候选预览、人工采纳、Reject / Retry 和视频播放。最小窗口优先保留追溯文本，预览随可用空间缩小。
