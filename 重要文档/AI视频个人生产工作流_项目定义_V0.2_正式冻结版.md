## 1. 项目名称

**AI 视频个人生产工作流**

英文工作名可使用：**Personal AI Video Production Workflow**。  
如需强调工程属性，可使用：**AI Film Production Harness**。

以上名称均指向同一项目，不代表商业产品名称。

---

## 2. V0.2 的重新定义

本项目是一套面向个人真实 AI 视频 / AI 短剧生产的：

> **规范剧本驱动的资产准备、媒体生成、人工审核、局部返工、轻剪辑与交付工作流。**

它的核心价值不是“提供一个生成按钮”，而是：

> **把长期 AI 视频生产中最容易产生的素材混乱、引用混乱、命名混乱、状态混乱、返工混乱和工具切换摩擦压缩掉。**

系统通过少量明确规则，把生产所需的信息提前写入规范剧本，再由系统自动完成：

```text
剧本声明生产需求
↓
扫描资产需求
↓
检查素材库
↓
缺什么补什么
↓
自动调用参照资产
↓
生成候选
↓
人工红 / 黄 / 绿审核
↓
轻剪辑与局部返工
↓
输出
```

## 3. 项目目标

### 3.1 第一目标：形成真实、可解释的能力证明

本项目仍以就业 / 作品集中的能力展示为第一目标。

它需要证明：

1. 能理解 AI 视频真实生产过程，而不是只会单次生成；
2. 能把剧本、视觉资产、音声资产、视频参照、生成任务、审核、返工、剪辑与输出组织成一条稳定工作流；
3. 能识别“哪些信息值得结构化，哪些创作内容应该保持自然语言自由”；
4. 能处理人物、年龄、服装、音声、场景、关键物件与镜头参照的一致性问题；
5. 能把图片、音频、视频三类 API / Provider 组织在同一生产系统中；
6. 能合理利用成熟开源项目、API、CLI、现有播放器和 NLE，而不是重复造轮子；
7. 能通过真实作品和真实操作对比说明工作流为什么更快、更稳、更不乱；
8. 知道哪些判断必须保留给人。

最终展示的不是“做了一个界面”，而是：

> **能够设计、运行并持续优化一条真实的 AI 视频个人生产系统。**

### 3.2 第二目标：真实可用

系统必须优先服务真实生产。

不接受：

> **为了展示而存在，但真实使用反而增加步骤的核心功能。**

如果某个设计不能减少真实摩擦，就不应因为“看起来完整”而保留。

## 4. 最高设计原则

### 4.1 剧本是生产源头

正式剧本不是普通文稿，也不是数据库表格。

它是：

> **人可以自然阅读，同时能够让系统稳定推导生产需求的轻量生产语言。**

系统不得要求用户在正式生产阶段反复重新声明已经写进剧本的内容。

### 4.2 结构化必要信息，自由描述创作内容

只有当结构化能够直接换来以下价值时，才值得强制结构化：

- 精确调用；
- 资产复用；
- 一致性；
- 缺失检测；
- 流程控制；
- 状态恢复。

纯粹用于表达镜头创意、动作、表演、对白与摄影语言的内容，优先允许自然语言。

原则：

> **不为了机器解析，把创作写成数据库。**

### 4.3 消灭操作摩擦，保留判断摩擦

系统优先消灭：

- 找文件；
- 手动命名；
- 重复上传参照；
- 重复绑定人物 / 场景 / Voice；
- 手工检查缺失资产；
- 候选素材整理；
- 状态恢复；
- Provider 之间的机械切换；
- 重复导入剪辑区。

系统不替代：

- 创意判断；
- 剧本取舍；
- 镜头判断；
- 审美判断；
- 选片；
- 是否重抽；
- 是否改资产；
- 最终剪辑节奏；
- 最终质量判断。

### 4.4 准备阶段多想一点，生产阶段少做很多

本项目接受：

> **前期剧本要求更严格、填写内容更多，以换取几十个、几百个镜头中的长期效率。**

前期结构化不是负担本身，而是对后续重复劳动的提前消除。

### 4.5 有限规则优于无限兼容

本系统不追求兼容任意自由格式。

允许要求用户先阅读一份简短使用说明，学习少量固定规则。

目标是：

> **有限规则 + 明确说明 + 高效率执行。**

### 4.6 核心生产语义独立于 Provider 与模型

具体模型、Provider、文件格式、API 方言、UI 框架和 NLE 都属于可替换外围能力。

系统长期保留的是：

- 剧本语义；
- 资产引用；
- 候选与审核状态；
- Selected / 可用关系；
- 返工关系；
- 时间线与交付关系。

### 4.7 旧工程是底座，不是约束

此前 A-01 ～ A-08、UI-Final 与已有代码视为：

> **已经验证过一批技术能力的现成底座。**

后续：

- 能直接用的直接用；
- 稍改即可复用的就改；
- 与新主链冲突的可以删除；
- 旧抽象失去价值时可以废弃；
- 不为了保留旧代码扭曲新产品；
- 不承担不必要的向后兼容负担。

### 4.8 不过度验证

已经可靠证明过的基础能力，不重复大规模验证。

原则：

```text
改了什么
↓
重点验证什么

没改且已有可靠证据
↓
不重复折腾
```

真正需要验证的是新主链及发生变化的接口。

### 4.9 UI 好看是硬要求

V0.2 的 UI 验收标准不是“能用”。

而是：

> **可用，并具有展示级视觉完成度。**

界面应具有明确设计意图、统一视觉语言和现代创作工具气质。

不接受：

- 默认控件堆叠；
- 仅功能可点；
- 内部后台感明显；
- “最后再美化”的施工方式。

允许：

- 复用成熟 UI 组件；
- 参考优秀创作工具 / 影视工具的视觉语言；
- 自行设计组件；
- Codex 自行生成、组合或处理 UI / Demo 视觉素材。

视觉素材生成方法不冻结，只要求结果满足视觉质量、来源边界和生产真实性要求。

## 6. 剧本层级

项目采用：

```text
影片 / Project
↓
章节 / Episode / Chapter
↓
镜头 / Shot
```

### 6.1 影片

影片是最高层生产单位。

最低要求包含影片名称。

### 6.2 章节

章节是独立生产与交付单元。

章节可以是：

- 约 1 分钟的短剧一集；
- 更长的视频章节；
- 任意可独立生产、审核和输出的内容单元。

章节时长不固定。

系统应允许同一套心智从 1 集扩展到 100+ 集。

### 6.3 镜头

镜头是正式生产的基本单位。

用户按章节逐镜生产，镜头之间允许通过连续性描述、共享资产和参考素材保持前后关系。

## 7. 剧本基础语法

### 7.1 `/`：固定位置分隔

`/` 用于结构化行中的固定位置字段。

位置本身决定语义，系统不应依赖 AI 猜字段含义。

### 7.2 `-`：空位 / 默认 / 不指定

`-` 表示该位置存在，但本次不指定或不需要。

不同位置可有具体语义：

- 年龄 `-`：不额外约束年龄；
- 服装 `-`：不额外约束服装；
- 音声 `-`：不要求该人物 Voice / 对白生产。

音声为 `-` 不等于整个镜头绝对静音；环境声仍可独立存在。

### 7.3 `【】`：完整参照资产

`【】` 表示：

> **括号中的内容被视为一个完整、可复用、具有明确参照素材的资产。**

示例：

```text
【孙笑川/-/病号服】
【便利店/雨夜】
【红伞.破损】
【门内后退跟拍】
```

`【】` 的具体媒体类型由使用上下文决定：

- 角色视觉上下文 → 图片参照；
- 环境上下文 → 背景图片参照；
- 物件上下文 → 物件图片参照；
- 镜头上下文 → 视频参照。

### 7.4 视觉与声音不得合并为一个完整资产

角色行固定为：

```text
人物 / 年龄 / 服装 / 音声
```

允许：

```text
孙笑川/老年/病号服/虚弱
【孙笑川/老年/病号服】/虚弱
【孙笑川/-/病号服】/-
```

不应把视觉和音声打包成：

```text
【孙笑川/老年/病号服/虚弱】
```

因为：

- 视觉变化不一定伴随声音变化；
- 声音变化不一定伴随视觉变化；
- 两者混合会破坏复用并产生组合爆炸。

## 8. 角色规范

角色结构固定为四个位置：

```text
1 人物 / 2 年龄 / 3 服装 / 4 音声
```

示例：

```text
孙笑川/老年/病号服/虚弱
```

解析为：

```text
人物 = 孙笑川
年龄 = 老年
服装 = 病号服
音声 = 虚弱
```

### 8.1 普通组合

普通写法：

```text
孙笑川/老年/病号服/虚弱
```

表示系统可以分别从人物、年龄、服装、音声等逻辑资产中寻找或组合参照。

### 8.2 完整视觉角色资产

```text
【孙笑川/老年/病号服】/虚弱
```

表示前三项视觉条件已有一份完整视觉参照；音声仍独立解析。

### 8.3 多人物镜头

多人物镜头允许连续写多行角色结构，一人一行。

每一行仍使用完全相同的四位置规则。

### 8.4 同值字段

字段语义由位置决定，因此不同字段可以出现相同文本值。

例如：

```text
孙笑川/老年/病号服/老年
```

机器仍能无歧义解析。

但使用说明中应建议：

> **为了人类可读性，尽量避免相邻位置使用完全相同且容易混淆的命名。**

---

## 9. 环境与背景音规范

环境结构固定为：

```text
环境 / 背景音
```

### 9.1 普通环境

```text
雨夜便利店/雨声、空调声
```

视觉环境为自然语言描述，不要求完整背景参照资产。

### 9.2 完整环境资产

```text
【便利店/雨夜】/雨声、空调声
```

表示：

- `【便利店/雨夜】` 是一份完整可复用的视觉背景资产；
- `雨声、空调声` 是独立的背景音要求。

### 9.3 无背景音

```text
【便利店/雨夜】/-
```

表示不额外要求背景音。

---

## 10. 物件规范

### 10.1 普通物件

普通、一次性、无需外观稳定的物件直接写在自然语言正文中。

例如：

```text
桌上放着水杯和手机。
```

### 10.2 关键物件

重要、重复出现、剧情关键或需要稳定外观的物件，使用完整资产引用：

```text
【红伞.破损】
【大剑】
【大剑.pro】
【大剑.promax】
```

`【】` 内的完整字符串就是独立资产名。

系统不需要理解 `.pro`、`.promax` 的语义，只需要把不同完整名称视为不同资产。

---

## 11. 镜头描述规范

镜头描述不强制使用 `/`。

原因：

> **景别、机位、运动、节奏等镜头语言不依赖资产引用也能工作，不值得为了结构化而增加用户负担。**

推荐自然语言：

```text
镜头：
从便利店门内侧拍摄，人物推门后镜头轻微后移，
保持中景，人物停下时缓慢推近，整体运动克制。
```

镜头描述可包含：

- 景别；
- 机位；
- 摄影机运动；
- 构图；
- 节奏；
- 时长倾向；
- 其他摄影要求。

### 11.1 视频镜头参照

素材库允许保存视频参照，用于镜头复刻或摄影运动参考。

示例：

```text
镜头：
【门内后退跟拍】
保持参考镜头的运动方式，但速度降低，结尾缓慢停住。
```

此时 `【门内后退跟拍】` 在镜头上下文中解析为视频参照资产。

## 12. 自然语言创作区

以下内容优先保持自然语言：

- 动作；
- 事件；
- 表演；
- 对白；
- 连续性；
- 备注；
- 镜头语言。

推荐示例：

```text
AAA/名称
01/集数

001/推门进入

【孙笑川/-/病号服】/虚弱

【便利店/雨夜】/雨声、空调声

镜头：
从门内侧拍摄，人物推门后镜头轻微后移，保持中景。

孙笑川推门进入便利店，右手拿着【红伞.破损】。
他收起雨伞，向柜台走了两步后停下。

表演：
疲惫，动作稍慢，但情绪克制。

对白：
孙笑川：今天雨真大。

连续性：
承接上一镜，右手仍有输液胶布。
```

具体 Parser 可以根据文件上下文和行序识别不同结构，但不得把自由创作区强制拆成大量字段。

## 13. 资产系统

### 13.1 资产由剧本反推

用户不应先手工建立复杂资产数据库，再回头写剧本。

标准逻辑：

```text
剧本
↓
扫描资产需求
↓
检查素材库
↓
已有 → 直接调用
缺失 → 进入生成 / 导入
↓
人工确认
↓
自动入库
```

### 13.2 视觉资产

包括但不限于：

- 人物基础视觉；
- 年龄状态；
- 服装；
- 完整角色视觉组合；
- 背景；
- 完整环境状态；
- 关键物件；
- 镜头视频参照。

### 13.3 音声资产

重要人物可以拥有固定 Voice / 声音身份。

逻辑上可表示为：

```text
人物 / 音声状态
```

例如：

```text
孙笑川/常态
孙笑川/老年
孙笑川/虚弱
```

具体实现可以是：

- 参考音频；
- Voice ID；
- Provider 内保存的 Voice；
- 其他可重复调用的声音身份机制。

文件格式不冻结。

### 13.4 图片与声音资产生产进入工作流

缺失的图片资产、声音资产可以直接在系统内生成。

用户也可以：

- 外部生成后导入；
- 直接打开文件夹加入素材；
- 替换素材；
- 重命名素材。

系统应重新扫描并同步，而不是把文件系统完全封闭。

### 13.5 剧本负责声明，不负责文件管理

用户写的是：

> **生产意图。**

系统负责：

- 文件映射；
- 自动命名；
- 自动保存；
- 资产关联；
- 缺失检查；
- Provider 调用。

内部可以维护稳定 ID，防止用户改名后历史关系彻底断裂，但具体实现不冻结。

### 13.6 资产变更影响提示

当已使用的资产被修改、替换或重命名时，系统应能够提示：

> **哪些镜头曾依赖该资产。**

系统不得自动销毁历史结果，也不得未经用户确认自动大规模重生成。

## 14. 图片、音频、视频三类生成能力

系统允许存在三类核心生成 Provider：

```text
Image
Audio
Video
```

它们不要求来自同一厂商。

### 14.1 图片

用于：

- 人物参照；
- 年龄 / 服装状态；
- 背景；
- 关键物件；
- 首帧；
- 其他视觉参考。

### 14.2 音频

用于：

- Voice 准备；
- 角色对白；
- 独立音声素材；
- 其他需要独立控制的声音。

### 14.3 视频

用于：

- 正式镜头；
- 视频参照；
- 原生视听生成；
- 接收已有音频作为生成 / LipSync 条件（当 Provider 支持）。

### 14.4 API 必须适合批量生产

系统应支持：

- 一次生成多个候选；
- Provider 原生批量；
- Provider 不支持批量时由系统拆成多个任务；
- 结果自动下载；
- 自动保存；
- 自动归属资产 / 镜头；
- 用户不必手工给每个候选命名。

具体 Job / Queue / Batch 技术实现不冻结。

---

## 15. 音声与视频的关系

音声不是视频的附属模块，而是一条可以独立存在、又能与视频汇合的生产线。

系统至少允许三种情况：

### 15.1 视频原生音声

视频模型直接生成画面与声音。

### 15.2 独立音声

音声由：

- 系统内 Audio API；
- 或系统外工具；

独立生成后进入当前镜头。

### 15.3 音声先行

当视频模型支持音频输入、口型驱动或声音条件时，可先确定音频，再作为视频生成条件。

### 15.4 无角色音声

例如：

```text
孙笑川/-/病号服/-
```

系统不应调用该人物的 Voice 生产链。

但环境声仍可由环境字段独立声明。

---

## 16. 生成候选与红黄绿审核

图片、音频、视频生成结果统一采用：

```text
生成
↓
看 / 听
↓
人工判断
```

### 🟢 Green / 可用

明确值得保留。

进入正常生产素材池。

一个资产 / 镜头允许存在多个绿色候选。

绿色不等于“永远最终选中”。

### 🟡 Yellow / 待定

当前不想立即决定。

保留，但默认不进入正常轻剪辑素材池。

黄色不是“中等质量评分”，而是：

> **决策缓冲区。**

### 🔴 Red / 废弃

明确不要。

保留历史，但不进入正常生产素材池。

原则：

> **连判断摩擦都不要强迫它在错误的时间发生。**

---

## 17. 镜头生产与返工逻辑

正式生产以镜头为单位。

### 17.1 模型没抽好

```text
要求没问题
↓
再抽
```

### 17.2 镜头要求写错

```text
修改当前镜头剧本
↓
继续生成
```

### 17.3 资产本身有问题

```text
回到资产层修改
↓
提示受影响镜头
↓
由用户决定是否重生成
```

### 17.4 素材没问题，只是剪辑不好

```text
进入轻剪辑处理
```

### 17.5 上层故事有问题

允许回到剧本更上层修改，只返工真正受到影响的部分。

核心原则：

> **哪里不满意，点哪里；为什么不满意，就回到对应层级。**

---

## 18. 轻剪辑定义

本项目需要真实但克制的轻剪辑能力。

推荐布局：

```text
左：素材
中：Preview
右：轻工具
下：Timeline
```

允许的核心能力包括：

- 拖入；
- 排序；
- 替换；
- 裁头尾；
- 分割；
- 删除；
- 吸附；
- 播放头；
- Undo / Redo；
- 简单音量 / 静音；
- 字幕显示与简单调整。

轻剪辑与生产允许往返：

```text
时间线发现问题
↓
跳回对应镜头
↓
换绿色候选 / 再抽 / 改剧本 / 改资产
↓
新结果进入素材池
↓
替换回时间线
```

未来允许开源，但开源不是当前施工目标。

## 22. 成功标准

### 22.1 产品结果

用户可以从规范剧本开始，经过资产准备、生成、审核、轻剪和返工，持续完成真实章节生产。

### 22.2 效率结果

系统应显著减少：

- 找文件；
- 重复上传；
- 手工命名；
- 资产状态记忆；
- 候选整理；
- 重新绑定；
- 返工定位；
- 工具切换与上下文恢复。

### 22.3 一致性结果

工作流能够稳定把正确的：

- 人物；
- 年龄；
- 服装；
- Voice；
- 环境；
- 关键物件；
- 镜头参照；
- 连续性描述；

交给生成模型。

模型最终是否完全遵守参照属于模型质量问题，仍通过候选、审核与重抽收敛。

### 22.4 UI 结果

核心页面必须具有展示级视觉完成度。

截图本身应能够作为作品集材料，而不是只证明“功能能点”。

### 22.5 工程结果

核心生产语义不依赖单一 Provider、模型、UI 或文件扩展名。

## 23. 本版本冻结

V0.2 正式冻结以下内容：

1. 剧本是整个系统的生产源头；
2. 影片 → 章节 → 镜头的层级；
3. `/`、`-`、`【】` 的核心语义；
4. 角色行固定为“人物 / 年龄 / 服装 / 音声”；
5. 环境行固定为“环境 / 背景音”；
6. 视觉与声音资产分离；
7. `【】` 表示完整参照资产；
8. 普通物件自然语言、关键物件 `【】` 引用；
9. 镜头允许自然语言长描述，并允许视频参照资产；
10. 剧本反推资产需求；
11. 缺失资产可系统内生成或外部导入；
12. 文件系统对用户开放；
13. 图片、音频、视频三类 Provider 能力；
14. 批量生成、自动保存与自动归属是核心方向；
15. 红 / 黄 / 绿审核语义；
16. 返工回到真正出问题的层级；
17. 轻剪辑与生产可往返；
18. 有限规范换取长期效率；
19. 旧工程是底座，不是约束；
20. 不过度验证；
21. UI 好看是硬性验收要求；
22. Codex 可自由选择合理方法生成视觉素材；
23. Human Gate 保留；
24. 项目不扩张成完整 AI Film Studio。

## 25. 一句话定义

> **这是一套以规范剧本为生产源头、以可复用参照资产保持一致性、以图片 / 音频 / 视频生成与人工红黄绿审核为核心、通过轻剪辑和局部返工持续收敛成片的个人 AI 视频生产工作流；它的目标不是替人创作，而是让长期 AI 视频生产更快、更稳、更不乱。**
